# ReXGlue SDK patches

The setup tool applies these to the [ReXGlue SDK](https://github.com/rexglue/rexglue-sdk) at commit `c94f5ebdcb3c9d1a460ca48e04f9758448f8d518` before building it.

| Patch | What it does |
|---|---|
| `0001` | Lets codegen handle several DLLs that share a base address. All CoD3 level DLLs load at 0x89000000. |
| `0002` | Raises the `video_mode_refresh_rate` setting's limit to 1000 Hz. (Since 0008 the game keeps a 60 Hz video mode and uses `guest_vblank_rate` instead.) |
| `0003` | Loads recompiled modules by their target name on Linux (`lib<name>.so`). |
| `0004` | Lets mid-asm hooks take the whole guest context (`ctx`) and memory base (`base`), which the script-thread fibers need. |
| `0006` | Fixes how the GPU shader translator reads the second component of a scalar ALU operation that shares source 3 with a three-operand vector operation (Z, not X). This is the stretched grass in Call of Duty 3 (vertex shader `4B4E6FDA02FB39C3`); ported from [Xenia Canary PR #1149](https://github.com/xenia-canary/xenia-canary/pull/1149). Only the GPU plugin is rebuilt. |
| `0007` | Keyboard binds: a key bound on its own (for example `Shift` for sprint) also fires while other modifier keys are held, unless some bind uses that key with modifiers (then those binds keep matching exactly). Before, a bare `Shift` bind could never fire. |
| `0008` | Makes the guest's vblank rate a live setting (`guest_vblank_rate`, Hz; 0 = the video mode's rate). CoD3 runs it at 1000 Hz so waiting for vblank never caps or rounds the frame rate; `com_maxfps` is the limit (see `recomp/src/game/frame_rate.h`). |
| `0009` | Keyboard and mouse: the mouse's side buttons (back and forward, SDL's X1 and X2) reach key binds as `MB4` and `MB5` (also accepted: `MOUSE4`/`MOUSE5`, `MM4`/`MM5`). Before, only the left, right and middle buttons were passed on. |
| `0010` | The emulated EDRAM has 4096 tiles (20 MB) instead of the Xbox 360's 2048, so a game can draw at a resolution whose color and depth don't fit in 10 MB (Call of Duty 3 at 1920x1080, or 1280x720 with its 2x MSAA). A resolve's base tile gets a 12th bit (bit 31 of `ResolveEdramInfo`). Surfaces within 2048 tiles behave as on the console. The precompiled Vulkan resolve shaders are edited to match by `c3w/sdk_shaders.py` right after the patches (the wrap and the base bit; checked word by word); the D3D12 ones are left as they are, so on D3D12 the game stays within 2048 tiles. |
| `0011` | Codegen: a `[names]` table (`0x82536DD0 = "Com_Frame"`) gives functions the analysis finds readable names in the generated code, without adding or changing any function. A name for an address that isn't a function start is skipped; a name used twice stops the codegen. CoD3's table is `recomp/config/names.toml`, made by `tools/gen_codegen_names.py` from the symbol map. |
| `0012` | Performance: running totals of the GPU emulation's work (`rex/graphics/gpu_stats.h`: frames, draws, resolves, render target transfers, submissions, waits for the GPU and their time, resolve readbacks, occlusion queries, uploads, texture loads, write-watch faults), read by the game's performance readout. Occlusion query results are delivered when the GPU has finished them instead of stopping the GPU emulation to wait at every query (the guest polls for them, as on the console). `readback_resolve` no longer copies back resolves into a buffer the game has presented with a swap (its CPU never reads the picture on screen; `readback_resolve_skip_frontbuffer`), and `readback_resolve_log` lists each new destination that is copied back. Vulkan and D3D12. |
| `0013` | The window: a dialog that only draws on top of game frames (a HUD) can say it needs no continuous repaint. Before, any overlay made the window repaint and present as fast as the GPU could on Linux (no vblank wait for the UI), which used most of the GPU for nothing. UI-only repaints are paced at the display's refresh rate (`ui_refresh_rate` overrides it); game frames are shown as soon as they're ready. Also a fullscreen refresh rate (`Window::SetFullscreenRefreshRate`: an exclusive display mode at the desktop's resolution, or borderless when 0) and the rates the display offers. |
| `0014` | The draw resolution scale can change while the game runs: `draw_resolution_scale_x`, `draw_resolution_scale_y` and `resolution_scale` are live settings. At the end of the next frame the GPU emulation waits for the GPU and recreates what the scale is baked into (the EDRAM buffer and render targets, the texture cache with its scaled resolve buffer, all translated shaders and pipelines); the device, shared memory and guest shaders are kept. Setting the three one after another makes one rebuild: a request is applied once it has stayed the same for a frame. The picture stops for a moment while shaders are rebuilt, and render targets and resolved textures start over. If the new scale can't be set up (no memory for its scaled resolve buffer), 1x is used and the log says so (`GPU: draw resolution scale changed to ...`). Vulkan and D3D12 (D3D12 compiled, not run). |
| `0015` | Linux: the guest memory's shared-memory file (`/dev/shm/xenia_memory_*`, the size of the console's address space) is unlinked as soon as it is created. The open descriptor keeps it alive while the game runs, and the system frees it when the game ends however it ends. Before, only a clean exit removed it, so every crash, kill or forced close left one behind, holding the RAM the game had used until the next reboot (found 2026-10-10: 27 of them filled 5 GB of the test machine's 8 GB and the system killed the game). |
| `0016` | Texture replacement (the HD textures): with `texture_replacement_path` set to a pack folder (an `index.tsv` and DDS files, made by the ripper's `cod3-hd-pack`; CoD3's is `data/cod3/hd_textures`, the waifu2x textures, at whatever scale they were made, in the game's own BC formats; 32-bit DDS files hold B, G, R, A, the memory order of the guest's A8R8G8B8 textures after the byte swap), a texture whose guest data is in the pack is drawn with the pack's image. When the texture cache is about to create a host texture for a 2D k_DXT1, k_DXT2_3, k_DXT4_5, k_DXN or k_8_8_8_8 texture (not a resolve target), it computes the key from the guest memory exactly like the ripper's `hd_keys.tsv` (XXH64 of the base level, untiled and byte-swapped; a base level with a side of 16 texels or less lies 16 texels into its packed mip tile, and is read from there); if the index has it with the same size and format, and the host keeps that format natively (BC1/BC2/BC3/BC5, R8G8B8A8), the host texture gets the image's size, whatever it is (no scale is assumed, and it needn't be a whole number: any size with the guest's aspect ratio to within the ripper's rounding, `|w × guest_h − h × guest_w| ≤ 4 × (guest_w + guest_h)`, and within the GPU's largest texture), and mip levels: the file's, but no more than the guest's plus round(log2(scale)), scale being the ratio of the longest sides, so its smallest level is about the guest's smallest; it's uploaded from the file and guest data is never loaded into it. Shaders keep the guest's size from the fetch constant and the GPU picks levels from the host size, so any scale samples at the right detail. Its memory stays watched: when the game rewrites it, the key is computed again, and if it differs the texture is retired (destroyed once the GPU is done with it) and a normal one takes its place. The index is read once, when the GPU starts, so the setting must be set before that (it exists once the GPU plugin is loaded); a missing or broken index is logged once and the feature stays off. `texture_replacement_log` logs every candidate texture's key, size, format and whether it was replaced; the counters `textures_replaced` and `textures_not_in_pack` are in `rex/graphics/gpu_stats.h`. Replaced textures take the square of the scale in memory (4x at 2x), which counts toward the texture cache's memory limits. A second pack, `texture_replacement_user_path` (CoD3's `data/cod3/user_textures`, the player's own pictures made by the ripper's `cod3-user-pack`), is read after the first and wins for a key in both; its images are checked against the original's alpha (an opaque original makes the image opaque; one with transparent parts may not get more see-through, to within 2%). The policy is live: `texture_replacement_enabled` turns replacement off and on, and `texture_replacement_allow_list` (a file of keys) limits it to those keys, for example in a multiplayer match (then every image is alpha-checked too); when it changes, every texture binding is looked up again and textures whose decision changed are retired and made again. Packs are untrusted input: an index `file` must be a plain relative path inside the pack (no absolute path, `..`, backslash, drive letter or control character, at most 255 bytes) and the opened file, links followed, must be inside the folder; DDS headers are checked before anything is allocated (no DX10, cube or volume, sides 1 to 16384 and the GPU's limit, at most 15 levels and no more than a full chain, the file exactly as long as its levels); index and allow list files are size-capped; `texture_replacement_memory_limit` (MB, default 4096) caps the replacement images alive at once. A broken file is skipped with one log line. Vulkan and D3D12 (D3D12 compiled, not run). |
| `0017` | Logs "Too few processor cores - scheduling will be wonky" once instead of on every GPU interrupt, which on a PC with fewer than 6 logical CPUs was about 1,000 identical lines a second at CoD3's 1000 Hz vblank, each written to disk. |
| `0018` | Linux and macOS: `PulseEvent` releases exactly the threads waiting at that moment (one for an auto-reset event, all for a manual-reset one) by owing them wake-ups, instead of setting the event for 10 µs, which a busy PC's waiters often missed; that hung CoD3's level loads, because its job system wakes its worker threads with `PulseEvent`. |
| `0019` | Linux and macOS: waits on several objects, and the 1 ms slices of alertable waits, sleep until their time-out instead of spinning through its last millisecond (the Audio Worker used a whole CPU core that way). |
| `0020` | Vulkan: a draw checks for memexport ranges before it looks up the readback setting by name, a lock and a string search that every draw paid for although CoD3 has no memexport ranges. |
| `0021` | `SharedMemory::RequestRanges` (a few calls per draw) reuses one vector for the merged ranges instead of allocating a new one each call. |
| `0022` | The idle GPU command thread yields 501 times before it sleeps only with 6 or more logical CPUs (as before); with fewer it sleeps at once, so it doesn't take time slices from the game's threads (setting `gpu_idle_spin_count`, -1 = this automatic choice). |
| `0023` | Windows: a library given by its full path (the GPU plugin next to the executable) finds the DLLs it needs in its own folder first (`LoadLibraryExW` with `LOAD_WITH_ALTERED_SEARCH_PATH`), whatever the current folder is (a launcher, Wine or Proton may start the program elsewhere); a recompiled module DLL is also found under MinGW's `lib<name>.dll` name; the GPU plugin is found as `rexgpu-<name>.dll` or `librexgpu-<name>.dll`, and a load failure logs the Windows error and the paths it tried. The executable's folder comes from Windows itself (`GetModuleFileNameW`) instead of the C runtime's `_get_wpgmptr`. (Owner, 2026-10-11: under Proton the .exe "complained about not having module 'xenos'". The package had the plugin, but a MinGW build names it `librexgpu-xenos.dll` and the SDK looked only for `rexgpu-xenos.dll`; the level DLLs had the same `lib` prefix problem. Since no import table names the plugin, the setup tool now also looks it up by name when packing.) |
| `0024` | Performance: `readback_resolve` copies back only the resolves the game's CPU accesses (`readback_resolve_cpu_reads_only`, default on, live; off = as before). The others stay on the GPU, as with readback off, and are read-watched: a new memory watch (`rex/system/xmemory_read_watch.h`, what Xenia's access callbacks call data providers) keeps their pages inaccessible in the guest's physical views (0xA0000000, 0xC0000000, 0xE0000000) until the guest touches them. The first access to one (a read or a write, by any thread through those views) waits while the GPU command thread copies that resolve back on the spot (it waits for the GPU, like `full`), then goes ahead with the current data; from then on that destination is copied back after every resolve as before. So no access sees older data than before, whenever the CPU starts reading (a light flare coming into view). The GPU thread itself can't wait for itself (a guest interrupt callback there sees the older contents once), and a wait longer than `readback_resolve_cpu_wait_limit_ms` (default 10000; the copy waits for the GPU, which takes seconds with a software Vulkan driver) goes ahead with the older contents and logs a warning; the late copy is then never written. More than 256 destinations: new ones are copied back as before. The watch is dropped where memory is written past the views (a file read into it), decommitted, released or made writable again by a protection change (that data isn't wanted anymore, like the write watch's invalidation); a commit or another protection change keeps it, and the write watch never loosens a watched page. A host file write (`XFile::Write`) triggers it first, as its system call can't. The watch's state lives in `xmemory.cpp`, so `xmemory.h`, which every recompiled game file includes, is unchanged (an SDK update doesn't rebuild the game). `readback_resolve_log` lists destinations as they are skipped, first accessed (with the wait) and copied from then on. Saint-Lô in the cloud at 1280x720 (`readback_resolve = fast`, intro): 9.6 readbacks and 14.1 MB a frame on average (up to 21 MB) before, 0.1 and 0.35 MB after (up to 3.7 MB): the game's main thread reads one destination, 1280x736x4 (most likely the light flares' visibility test), and none of the other 13. With `full` (the owner's last setting: 12.9 GPU waits, 4.3 ms a frame) that is about one wait a frame instead. Vulkan (run) and D3D12 (compiled and linked in the Windows build, not run); the readback code of both is split into `EnsureReadbackBufferSlot` and `RecordResolveReadbackCopy`, which also fixes a copy recorded into a closed submission after a readback buffer had to be replaced. |
| `0025` | Multiplayer networking for system link (LAN), the same on Linux, Windows and Wine. **Sockets:** the guest's Winsock numbers are translated to the host's instead of passed through: `setsockopt` options (`SOL_SOCKET` 0xFFFF with `SO_BROADCAST`, `SO_REUSEADDR`, `SO_RCVBUF`/`SO_SNDBUF`, `SO_LINGER`/`SO_DONTLINGER`, timeouts and the others in `rex/net/socket.h`; `TCP_NODELAY`; the console's encryption switches 0x5801/0x5802 are accepted and ignored; anything else is refused with WSAENOPROTOOPT), with values read big-endian; `ioctlsocket` `FIONBIO` (0x8004667E, non-blocking via `fcntl` on POSIX) and `FIONREAD`; message flags; and errors, so `WSAGetLastError` gives Winsock codes on every host (`errno` translated on POSIX: "would block" is 10035). Before, Linux refused CoD3's `SO_BROADCAST` and `FIONBIO`, and its network library gives up when either fails. `sendto`/`recvfrom` now build host addresses in network order (before, `sendto` reversed the destination's address and port bytes and `recvfrom` the source port); a datagram too big for the buffer fails with WSAEMSGSIZE on Linux too (`MSG_TRUNC`); sockets aren't inherited by child processes; Windows UDP sockets don't report ICMP "port unreachable" as WSAECONNRESET (as on Linux and the console); `select` passes the right descriptor count on POSIX. **VDP** (protocol 254) is sent as UDP; the guest writes and reads its 2-byte game data length itself (CoD3: `bdPacket` at 0x821BBE20), and a datagram whose length field is longer than the datagram is refused on send and dropped on receive. **XNet:** `XNetGetTitleXnAddr` gives the PC's LAN IPv4 address (the default route's interface, or the one setting `net_interface` names by address or, on Linux, by name) with a MAC address field made from that address, so every PC computes the same XNADDR for a peer from its address alone; `XNetGetEthernetLinkStatus` reports a link while an interface is up; `XNetXnAddrToInAddr` returns the peer's own address and `XNetInAddrToXnAddr` the reverse (a peer not yet seen, a player joining, gets the XNADDR made from its address and the newest key); `XNetCreateKey` (system link key ids), `RegisterKey`, `UnregisterKey`, `UnregisterInAddr`, `Connect`, `GetConnectStatus` (a known peer is connected at once: there is no key exchange between PCs), `TsAddrToInAddr`, `InAddrToString`, `QosListen` and `QosLookup` (every target is answered at once, "contacted" at 10 ms if system link may reach it; CoD3 never frees the results, so the oldest of 256 are freed) work without Xbox Live; `XNetRandom` and the keys come from the system's cryptographic random source (before: every byte 0xBB). `XSessionCreate` fills a hosted session's info with a new key and this PC's address and registers the key. **Security:** every pointer and length from the guest is checked against mapped guest memory before it is used (also in `accept`, `select` and `WSASendTo`, which could overrun host memory before); packet sizes are the host's, never a field in the packet; sockets bind only where the game asks; with `net_lan_only` (default on) packets go to and come from only loopback, private (RFC 1918), link-local and the chosen interface's subnet addresses, and others are dropped and logged once; no name lookups, files or commands. Unit tests: `tests/unit/core/net_socket_test.cpp`. |
| `0026` | File names from the game stay inside the folders the game's drives are mounted on (security). A name the guest gives a file or folder becomes one part of a host path only when it is a plain name: not empty, `.` or `..`, and without `/`, `\`, `:` (a drive or a Windows stream) or control characters (`rex/filesystem/guest_name.h`). Before, a rename to `game:\..\..\file` moved the file out of the game folder, and on Windows a path part like `D:` reached another drive's folder. Creating, looking up and renaming files refuse other names, and nothing on a read-only drive (the game's own files) can be renamed; a content package's (save's) name is made plain (`..` becomes `_`), and the files of a package being installed must have plain names too. Normal game paths are unchanged. Also, the settings file the SDK saves (CoD3's `cod3.toml`) escapes quotes, backslashes and control characters in text values, so a value can't break the file or add settings of its own (before, a Windows path made the whole file unreadable). |
| `0027` | Codegen: the host `jmp_buf` behind the guest's `setjmp`/`longjmp` (`get_jmp_buf_map()` in the generated `<project>_pch.h`) is kept in a 16-byte aligned slot (`ppc_jmp_buf_slot`). On x64 Windows the C runtime's `setjmp` and `longjmp` (Microsoft's and Wine's alike) save and load xmm6-xmm15 with aligned SSE moves; `jmp_buf`'s 16-byte alignment is an attribute of the typedef and is lost as a template argument, so in the old `std::unordered_map<u32, jmp_buf>` every buffer sat 8 bytes off a 16-byte boundary and the first `setjmp` crashed the process with an access violation. In Call of Duty 3 that is the first script thread of a level (`ScriptThread_Run`, 0x824A6150): the Windows build, under Proton, reached the menus and loaded Saint-Lô, then ended without a word (owner, 2026-10-12 and 10-13). Linux and macOS behave as before (their `setjmp` has no alignment need). Regenerates every module's `_pch.h`, so the game rebuilds from scratch once. |
| `0028` | Windows: the SDK builds libmspack (the XEX decompressor) from the library's own `libmspack/libmspack/mspack` folder. The `cabextract/mspack` folder the SDK used holds only symlinks to those files, and a git checkout on Windows without symlink support (the default without Developer Mode) writes each symlink as a small text file holding its target, so the SDK build stopped at `lzxd.c:1:1: error: expected identifier or '('` (a Windows user's setup log, 2026-10-13). Same files, so nothing changes on Linux. |
| `0029` | Windows frame pacing. **Precise sleeps:** `rex::thread::Sleep` and `AlertableSleep` wait on a per-thread high-resolution waitable timer (`CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`, Windows 10 1803 and later; `::Sleep`/`SleepEx` as before where there is none), so a 1 ms sleep takes about 1 ms as on Linux (`nanosleep`) instead of waking on the system timer's tick: 1 to 2 ms with `timeBeginPeriod(1)`, 15.6 ms when Windows doesn't apply it (Windows 11 may drop a program's timer request while it thinks the window is hidden). The GPU's vblank thread and its command thread (the `WAIT_REG_MEM` on the swap flag after every frame, `wait` = 256 → 1 ms polls while `vsync` is on, the default) sleep in 1 ms steps every frame, so on Windows those set the frame rate's ceiling: a model of the two loops gives 32 fps at a 15.6 ms tick whatever the PC, and about 10-20% under Linux at 1 ms. Sleeps under 100 µs still yield; an APC still ends an alertable sleep. **UI ticks:** a new game frame (`ForceUIThreadPaintTick`) wakes a UI thread that is already waiting for the next vblank, instead of being shown up to a refresh later. **Present mode in words** (`rex/ui/present_mode.h`, new): the Vulkan presenter (immediate, mailbox, FIFO relaxed, FIFO) and the Direct3D 12 presenter (sync interval 0, tearing allowed or not; it also logs its swap chain now) say how they show frames, for the game's log. Linux and macOS: only the present mode text is new. |
| `0030` | The Vulkan GPU emulation's debug line about each presented frame (`XELOG_GPU PRESENT: ...`) is logged when the picture's sizes or format change, not for every frame. At the debug log level (`cod3_log_detail debug`) it was about 15,000 lines in three minutes, a 5 MB log file every few minutes and a formatted line and a disk write per frame (the owner's log, 2026-10-13). Nothing else changes. |
| `0031` | Measurements for the in-engine thread profiler (`recomp/src/game/thread_profiler.h`; the owner's 2026-10-13 rule that the game scales to the machine it runs on, measured in-engine). `rex/graphics/gpu_stats.h` version 2 adds the GPU command thread's busy time (`kGpuThreadMicros`), the time spent handing commands to the driver (`kSubmitMicros`) and the shaders translated while a draw waited (`kShaderTranslations`, `kShaderTranslateMicros`), on Vulkan and Direct3D 12. A new `rex/thread/thread_stats.h` adds up, for each host thread, how long it waited and on what: the game's own events and threads (`XObject::Wait`, `SignalAndWait`, `WaitMultiple`; polls with no time-out are left out), its sleeps (`XThread::Delay`), contended spinlocks (`KfAcquireSpinLock` tries once, then times the yield loop) and the contended global lock (`global_critical_region` tries the lock first and times only a real wait). Thread names: an unnamed guest thread is called `XThread` plus the address it starts at (`XThread8212A780`: the game's job workers) instead of a number, and on Linux a name longer than 15 characters is cut to 15 instead of being refused by `pthread_setname_np` (so the "Vulkan Pipeline" threads have names). The cost is a clock read at the start and end of each measured wait; nothing the game does changes. Supersedes the unmerged `dev/agents/cpu-cores/0016-gpu-thread-busy-time.patch`. |
| `0032` | The sound output device is a setting: `audio_device` (Audio), a device's name as `rex::audio::ListOutputDevices()` gives it (new `rex/audio/output_device.h`; the system's names, a repeated name gets " #2"), empty = the system default as before. It is live (a change is picked up at the audio thread's next frame), kept in the settings file, and checked every 2 s while set: when its device is unplugged the sound moves to the system default, and back when it returns. `CurrentOutputDevice()` names the device in use. Why: SDL 3 opens the system default by its name, which on Linux pins the stream to that sink (PipeWire `target.object`, PulseAudio's sink name), so a device picked in the system's mixer is replaced at every start; CoD3 restarts its process between missions, so the owner's choice was lost each time (reproduced 2026-10-15 with PipeWire 1.0.5 and WirePlumber 0.4.17). The log lists the outputs once and says which device each stream opened on and why. If every open fails, frames are dropped at their playing rate instead of the guest waiting for a callback that never comes. Linux and Windows (SDL 3 on both). |
| `0036` | Linux / macOS: a crash in code nothing claims ends the process. The fault handler returned from a SIGSEGV/SIGILL (SIGBUS on macOS) that no handler took, so the same instruction faulted again at once, about 13,000 times a second, and a crash looked like a hang at 100% of a core. Now it writes one line to stderr (`rex: unhandled SIGSEGV at address 0x...; passing it on, the process will end`) and puts the original handler back, so the fault ends the process (a core dump where the system makes them). Found when a runtime and a GPU plugin from different builds were paired. |
| `0037` | The window stops repainting on its own. The achievement toast dialog exists for the whole session and asked for continuous repaints (`ImGuiDialog::WantsContinuousRepaint`, default true; patch 0013), so the window painted and presented at the display's refresh rate (240 a second on a 240 Hz screen) on top of the game's own frames all the time: on the owner's PC the window thread ran at 93-97% of a core in every report, and each extra present took graphics card time from the game. Now it asks only while a toast is on screen (to fade it). Also a new counter, `kPresents` in `rex/graphics/gpu_stats.h` version 3: pictures the window presented, game frames and UI-only repaints together (`recomp/src/game/perf_stats.h` shows it a second). |
| `0038` | Who holds the global lock while a thread waits for it (`rex/thread/thread_stats.h` version 2: `ReadLockHolders`). On the owner's PC the GPU emulation thread waited 8-19% of its time for the SDK's global lock; each wait is now also counted by the thread that held the lock when the wait began, which the stall table shows as "global lock 19% (held by ...)". The holder is read from the lock itself (glibc keeps the owner's thread id in the mutex), so the uncontended path costs nothing more; elsewhere (Windows) it is 0, "not known". If the lock was released between the first try and the read, the waiter tries once more before it counts a wait. |
| `0039` | A progress signal from the GPU emulation (new `rex/graphics/gpu_progress.h`: `Count`, `Signal`, `Wait`), so a game thread that waits for the emulated GPU can sleep instead of spinning. The command processor signals after every write a guest thread may be polling for: the ring buffer read pointer write-back after each batch, scratch register write-backs (Direct3D's fences), `MEM_WRITE`, `COND_WRITE`, `REG_TO_MEM`, the `EVENT_WRITE_*` packets and occlusion query results (Vulkan and D3D12), and after every guest interrupt (the vblank too). `Signal` is one atomic add and one atomic load while nobody waits. Used by `recomp/src/game/gpu_wait.h`: the game's Direct3D spins on these values, which held its main thread's core at 100% whenever the GPU emulation was behind. |
| `0040` | The picture's colors (owner, 2026-10-15: "make sure it's rendering with bt.709 colorspace or make it match the user's colorspace"). (1) `kernel_display_gamma_type` / `kernel_display_gamma_power` (Xenia's names; default 2, BT.709, as before): the display `VdGetCurrentDisplayGamma` reports. The console's Direct3D builds the hardware gamma ramp from the game's ramp for it: an sRGB display (1) gets the game's ramp as it is, an HDTV (2) gets BT.709's transfer curve on top. (2) `display_output_transfer` (`none` / `bt1886`): shows the picture the way an HDTV does (BT.1886, gamma 2.4, black at 0) on an sRGB PC display, folded into the gamma ramp the presenter already applies (256-entry table and PWL; no extra pass, a change shows at the next frame; within 0.04/255 of the exact curve). BT.709 and sRGB share primaries and white point, so only the tone curve changes. The game layer picks both from `cod3_color_space` (`recomp/src/game/color_output.h`). |
| `mingw/0005` | Only for the Windows game built on Linux with [llvm-mingw](https://github.com/mstorsjo/llvm-mingw) (see `cross/mingw/README.md`); applied right before that build: libc++'s missing `clock_cast`, the `__uuidof` spelling and COM interface IDs, no MSVC-only `__try`, and a `.def` file that exports the kernel functions (named `__imp__*`, which MinGW's automatic DLL export skips). Kept apart so it never changes the Linux SDK's headers (which would make the Linux game rebuild from scratch). |
