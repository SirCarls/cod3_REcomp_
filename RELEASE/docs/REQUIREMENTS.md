# COD_3_WAW — requirements, workflow and status

This is the project brief as given by the project owner, how the project is built and developed, and where each item stands. Where each fact comes from is in [SOURCES.md](SOURCES.md).

**Status words used below:**

- **Done:** implemented and tested as described.
- **Built:** implemented and compiles, but not yet checked in game.
- **In progress / Planned:** being worked on / agreed but not started.
- **Won't do:** ruled out; the reason is in [section 7](#7-wont-do).

## 1. Goal

- **A native remake in Rust** (based on [IW4L](https://github.com/vladtrc/iw4L)) for Linux and Windows. **Call of Duty 3** (Xbox 360) is the base game: its maps, models, sounds and campaign are ripped from the player's disc, and its campaign scripts are rewritten in Rust. **World at War** content (weapons, zombies, maps) is ripped from the player's copy and added on top.
- **The static recompilation of Call of Duty 3** (ReXGlue SDK) is the research reference for formats and game behavior. It is also an optional playable build until the Rust engine plays the campaign.
- **Players supply only their own games:** the Call of Duty 3 disc image, and optionally World at War. No game data is published.
- **Unreal Engine 5 export** of the ripped assets is a wanted extra.

## 2. Ground rules

These apply to every file in the project.

- **No personal information** in anything published: no personal paths, user names or details of anyone's computer. `tools/check_repo.py` fails CI on personal paths and game data.
- **No hard-coded paths.** Paths are relative to the project folder or come from the system (Steam's library list, the registry, environment variables), and work with both Windows and Linux path rules.
- **Safe to run and to build.** Downloads are pinned and checked (SHA-256, or a Microsoft signature for Microsoft's own installer). Archives can't write outside their folder. Folders are only deleted inside the work and output folders, never anything overlapping the inputs. The [README's Safety section](../README.md#safety) has the details.
- **Never touched:** the player's disc images, the World at War folder (including its `mods/` folder, which is ignored) and their downloads are only read, never changed or deleted.
- **Native only.** Nothing ships or runs through Wine or Proton. Neither game's executable is run, and no patch, mod or map installer is run: installers are unpacked. ~~One exception (owner, 2026-10-13): Xenia Canary in the cloud for Xbox 360 cross-play tests.~~ **Withdrawn 2026-10-16** with the Xbox 360 cross-play plan (owner: "exclude the plan for cross platform play with xbox360 it isn't a good idea/within reason"): no exception; Xenia is not run.
- **No DRM removal.** World at War's Steam DRM is not touched; World at War is never run.
- **Readable code**, and every source recorded in [SOURCES.md](SOURCES.md). The game itself too, toward the Rust port (owner, 2026-10-10: "get this game to as readable code as possible"): a symbol map names 2,242 of `default.xex`'s 19,083 functions and 585 globals with evidence (`recomp/config/symbols.toml`, made by `tools/name_functions.py`; RTTI, command tables, self-naming strings, Quake III matches, and a second pass by call-graph structure: the game's `vmMain` switch, `VM_Call` numbers, the cgame/renderer tables, the level-script interface). These names are now in the generated code and our hooks (`recomp/config/names.toml`, 1,608 functions, via SDK patch 0011: calls read `Com_Printf(ctx, base)`, hooks `REX_HOOK_RAW(CheatsOk)`), and [ENGINE.md](ENGINE.md) maps the engine's parts for the Rust port. Next: name more (library signatures for D3D/FMOD/SpeedTree/CRT, the level-script interface table, the `vfunc_N` slots) and write down each system before it moves to Rust.
- **Scales to the machine it runs on, in-engine** (owner, 2026-10-13: "the game needs to scale to what the machine actually has. I want this to be in-engine"). The port reads the machine at start (cores and how they're grouped, memory, graphics card and its memory) and sizes its threads, caches and defaults from that, from a 2-core laptop to a 24-thread desktop. It doesn't copy the Xbox 360's six threads or 512 MB. Finding what slows a frame happens inside the game (profiler and readouts in the overlay and F2, recordings written by the game), with no outside tools needed. Plan: `dev/agents/hw-scaling/PLAN.md` (private notes).
- **One multiplayer game across PC platforms** (owner, 2026-10-16: "exclude the plan for cross platform play with xbox360 it isn't a good idea/within reason"; earlier, 2026-10-13: "I really want to make the pool of players as large as possible"). The recomp on Linux and on Windows and the Rust engine play in the same match; Xbox 360 consoles, a custom Xbox 360 copy and Xenia are out of the plan (the 2026-10-13 plan for them is dropped). The recomp runs the console's own network code, so its messages are the wire format the Rust engine speaks to play with recomp players; the console-exact rules that existed for Xbox 360 players no longer bind the network design (the Rust decomp's console layer stays exact as its correctness reference). Dedicated servers are in the plan (7.2). World at War content is not part of CoD3's multiplayer; Call of Duty: United Offensive is a reference for the protocol, not a platform to join (owner, 2026-10-13).
- **Engine loops are fast and never choke** (owner, 2026-10-13: "make sure the loops are really fast and don't choke"): no allocation per call in what runs every frame, time at most in proportion to the input, exact console arithmetic without slow library calls, every engine function measured ([DECOMP.md](DECOMP.md#speed)). Never at the cost of the game's results or speed (game time follows real time).
- **Call of Duty 2 and United Offensive are decompiled too, Rust first** (owner, 2026-10-13: "Add both cod2 and codduo to the list to be decompiled (exclude cross platform play for now)"; "rust should be the priority, allow for cross platform play between cb copy and the rust version"). Each game's Rust version plays with the owner's CB (PC) copy of the same game, so the PC protocol is kept byte for byte ([PC_MULTIPLAYER.md](PC_MULTIPLAYER.md)); no Xbox 360 cross-play for these two for now, and they don't join Call of Duty 3's matches. New copies for the Rust version come from Steam or CB installs on Windows and Linux and hold only the data archives: the executables, and Steam's DRM inside them, are never copied, run or bypassed, and no Steam emulator is used ([NEW_COPY.md](NEW_COPY.md)). What one decomp learns goes into [DECOMP_SHARED_NOTES.md](DECOMP_SHARED_NOTES.md).
- **Settings live in the game's own menus** (owner, 2026-10-09). The recomp's F2 window is a fallback only.

## 3. Workflow

### 3.1 Building the game (players)

The player puts their games in `input/` (or picks them in the setup tool), starts `setup.sh` / `setup.bat` and presses **Build**. The setup tool then runs these steps; each one is skipped when its result is already there:

| # | Step | What it does |
|---|---|---|
| 1 | Checking inputs | Finds the Call of Duty 3 disc image and the World at War source (Steam folder first; otherwise the Xbox 360 or PC disc, plus map pack downloads). Checks `default.xex` against the supported release (*Call of Duty 3 (USA, Europe)*), and checks free disk space. |
| 2 | Tools | Finds the build tools and installs what's missing (see [4](#4-setup-tool)). |
| 3 | Call of Duty 3 game files | Copies the disc's files out of the image (read-only XDVDFS reader) into the output's `assets/`. |
| 4 | Ripper | Builds the Rust ripper (`engine/`), or uses a prebuilt one. |
| 5 | Ripping Call of Duty 3 | Rips the disc's archives into open formats in `data/cod3/` (DDS/PNG, glTF, JSON). |
| 6 | World at War | Optional, and not needed for the playable Call of Duty 3 (a checkbox in the setup tool, owner 2026-10-10: "stupid proof"; `--no-waw` on the command line). When ticked, rips the World at War fastfiles into `data/waw/`, taking only the map pack maps the disc lacks. |
| 7 | ReXGlue SDK | Downloads the SDK at a pinned commit with its submodules (repairing broken downloads), applies our patches, builds and installs it. *Only when the playable game is built, like steps 8 to 10.* |
| 8 | Recompiling Call of Duty 3 | Translates `default.xex` and the 15 level DLLs to C++ and compiles them. |
| 9 | Packaging | Copies the game and every library it needs (read from the binaries) into the output: an AppImage or `bin/` on Linux, `bin/cod3.exe` and DLLs on Windows. |
| 10 | The other system's version (optional) | The **Versions** boxes (Linux / Windows) pick what is built, on either system. On Linux, the Windows `cod3.exe` is built with llvm-mingw into `bin-windows/`. On Windows, the Linux AppImage is built inside WSL 2: a private Ubuntu 24.04 (Canonical's WSL image, checked against Canonical's SHA256SUMS) runs this same tool's Linux build and writes `CoD3-x86_64.AppImage` into the same output folder; it is removed at the cleanup unless "keep the built SDK" is on. WSL itself has to be turned on once by the owner of the PC (`wsl --install --no-distribution` in an administrator PowerShell, then a restart); the tool never does that. |
| 11 | Finishing | Writes both launchers (`Launcher.sh`, `Launcher.bat`) and `cod3_waw.json` (each version's executable, the sources). The Play page starts the version for the system it runs on. |
| 12 | Cleaning up | Deletes the work folder's temporary files (never the inputs). |

**Logs:** each run writes `output/logs/setup-<date>-<time>.log` (the last 10 are kept). The game writes `output/userdata/logs/cod3.log`.

### 3.2 Development

1. **The source** is the GitHub repository: `COD_3_WAW_Setup-tool/` (the setup tool, the recomp project in `recomp/`, the SDK patches in `patches/`), `engine/` (Rust), `docs/`, `tools/`.
2. **Changes are made and checked in a Claude session's own copy** before they reach the owner:
   - setup tool: `python3 -m unittest discover -s COD_3_WAW_Setup-tool/tests`;
   - repository: `python3 tools/check_repo.py`;
   - Rust: `cargo fmt --check`, `cargo clippy`, `cargo test`;
   - recomp: compiled against a Linux build of the game.
   The session's machine has no GPU. Its software Vulkan (SwiftShader) reaches the title screen in about 3 minutes but runs levels at about 0.05 fps, so **anything in a level is checked on the owner's computer**.
3. **SDK changes are patches**, applied in order by the setup tool: `patches/000N-*.patch`, and `patches/mingw/` only for the Windows build made on Linux. Generated files (`recomp/generated/`) are never edited, since the codegen rewrites them.
4. **Sync:** changed files are written into the owner's project folder through the Claude desktop app, then compared by size. The app can't move or delete files, so obsolete files are listed for the owner to remove.
5. **The owner builds and plays:** the setup tool as in 3.1, or `tools/run_local.sh` / `.ps1` / `.bat` for tests, checks and rips (results in `dev/logs/`).
6. **Every new session first checks the build logs** (the setup log, the game log, `dev/logs/`) for runs it hasn't seen, reports what they show and fixes what they point at.
7. **Session notes** (kept privately in the Claude project, not in the repository) carry the state from one session to the next: what was done, what's next, which logs were last checked.
8. **Publishing:** GitHub CI (`.github/workflows/ci.yml`) runs the checks on Linux and Windows. The release workflow attaches a zip with prebuilt rippers.

## 8. Won't do

- **WaW guns inside the recomp:** the two engines' asset formats differ; World at War weapons come in the Rust engine instead.
- **8 or more splitscreen players:** CoD3 supports 4.
- **8-player zombies:** stock World at War zombies supports 4.
- **128 players:** CoD3's engine limit is 24.
- **Perks from other games' assets (BO1–BO4, IW):** they would need other games' copyrighted assets. Perk *behavior* can still be scripted in the Rust engine.
- **DLSS:** proprietary, NVIDIA-only, and needs motion vectors a recomp doesn't produce. FSR is the upscaler.
- **Exclusive fullscreen in the recomp:** the SDK has none; borderless fullscreen is used.
- **Launching World at War** (Steam, Plutonium or Wine buttons): removed 2026-10-07; World at War's files are ripped instead.
- **Steam emulators or DRM removal** (SmartSteamEmu and the like, suggested 2026-10-13 as a source): the Rust versions never run the games' executables, so they need neither; new copies hold only the data archives.
